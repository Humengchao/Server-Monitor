# 指标历史的精度、统计口径与修复

## 历史查询

Web 详情页只在“指标”标签页选中时读取和绘制历史趋势；切到终端、进程或备注等标签页会取消尚未完成的历史请求，顶部最新采样仍按原频率刷新。返回指标页时，以当前时间为终点的预设立即更新；“昨天”和自定义区间保留原边界，已成功加载的数据不重复查询。浏览器标签页隐藏时暂停自动刷新，恢复可见后补上错过的刷新。

原始采样保留 24 小时，一分钟汇总保留 30 天，十五分钟汇总保留一年。普通历史图最多返回 500 个观测点，查询窗口最长 366 天；AI 历史使用相同的选层与加权逻辑，但按请求的点数上限分桶。

查询按展示精度选择数据层，不再只按数据年龄决定读取原始采样。较粗数据覆盖的区间不会重复读取更细数据；汇总层不存在、内部缺桶或尚未完成的尾部由细层补齐。最近五分钟使用原始采样，最近一小时的十五分钟汇总由更细数据替代，让维护重算前的迟到样本可见。更早的迟到数据需要重新执行对应区间的汇总才能反映在粗层。

普通图与 AI 的分层历史查询在各自只读事务内使用 `SET LOCAL jit=off`，避免短查询被 JIT 编译开销拖慢；事务结束后恢复连接原设置，不影响其他查询或数据库配置。

展示桶宽向上取整，分桶相对请求的 `since`，`until` 恰好落点时归入最后一个桶。查询边缘在细层覆盖完整时优先使用细层；细层已经全部或部分过期时，保留现存粗桶的平均值，其首点时间会限制在请求窗口内。粗桶被选中后，其区间内剩余细层不会再次计数。这是存储精度限制，不能从旧粗桶恢复秒级边界数据。

覆盖检查针对完整存储桶，而非只检查请求窗口内是否还有一条细层记录：一分钟桶比较原始样本总数与该桶的 `sample_count`；旧十五分钟桶逐分钟取“一分钟样本数”和“原始样本总数”的较大值，再求和比较。覆盖证据包含仍保存的无效 CPU 原始记录，但这些记录不会参与指标计算，避免把有效性过滤造成的计数减少误认成保留数据缺失、进而重新使用被污染的旧均值。若更细层只剩一部分且无法证明完整覆盖，就沿用粗桶的历史近似值，避免例如十五分钟只剩最后七个分钟时丢掉前八分钟的信息。

## 统计定义

主机延迟每轮取三包 ICMP 的平均值，发包间隔为 200ms，总超时四秒，并随采集器停止取消。延迟值 0 表示没有取得有效测量，不能解释成零延迟。

CPU、负载、已用内存、磁盘用量、网络和磁盘速率、延迟均按观测样本数加权：原始记录权重为 1，汇总记录权重为 `sample_count`。内存容量、累计流量和 uptime 保持原有最大值口径。汇总存储的舍入会带来小幅精度损失；加权消除了直接平均多个不等样本数均值的问题，但不能恢复已经舍入的原始数值。

CPU 必须为有限数且处于 0–100%。新无效样本整体拒绝保存；历史查询与重算也排除无效 CPU 样本的整条记录，包括它的其他指标。这保持了一个样本计数的明确含义，无效或缺失采样不会补成真实零负载。旧原始异常记录不会被修复工具删除，仍按正常保留周期清理。

当完整保留范围内的源记录全部无效时，普通维护和手动修复都会移除对应的旧汇总，避免旧均值恰好落在合法范围而被继续展示；清理也会传播到没有有效样本的十五分钟父桶。源数据已过期，或者根本没有源记录可证明该桶无效时，不会凭空删除旧历史。清理与重算在同一事务内执行。

`metric_maintenance_state` 中的 `weighted_metrics_v2` 记录新加权口径可使用的起点。初次运行新汇总逻辑时，该起点保守设为下一个十五分钟边界。更早的十五分钟汇总如更细源数据仍覆盖完整，查询会使用细层重新加权；更细源数据已经全部或部分过期时，保留旧汇总的历史近似值。修复工具全部成功后，才将起点提前至实际重算的范围。

## 手动修复保留范围内的汇总

修复工具不会随服务启动自动运行，也不读取 JWT、SSH 或其他应用配置。写入仅使用 `DATABASE_URL` 指定的数据库；连接串不会输出到日志。

先备份并确认备份可恢复，再在已部署的新后端容器中查看计划。以下命令应在当前发布使用的 Compose 配置环境内执行：

```bash
docker compose exec -T backend /app/metricsrepair
```

默认是 dry-run：只打印计划，不连接数据库、不写入。确认目标数据库和备份后执行：

```bash
docker compose exec -T backend /app/metricsrepair -apply
```

源码开发环境也可在 `web/backend` 中使用 `go run ./cmd/metricsrepair` 或 `go run ./cmd/metricsrepair -apply`。写入前通过受保护的环境配置提供 `DATABASE_URL`，不要把连接密码放在命令参数、聊天或提交记录中。

修复范围及限制：

- 最近 24 小时内的完整分钟，按小时重建一分钟汇总；最近 30 天内的完整十五分钟，按天重建十五分钟汇总。
- 两个范围的起点都额外避开保留边界后的两分钟，并向上对齐完整桶，防止并发清理删除首桶的部分源数据。进入十五分钟阶段前再次检查保留边界，因此实际起点可能比 dry-run 稍晚。
- 只处理已完成的桶，不重写窗口外的旧十五分钟记录。相比原始表，历史修复是有损源数据上的重算，不是恢复备份。
- 每批独立事务，查询与上下文上限十秒，锁等待上限一秒；整个运行包括数据库连接检查最多五分钟。支持 Ctrl+C 和 SIGTERM 取消。
- 失败时已提交批次保留，可重新执行；相同结果不会重复更新。全部批次成功前，不会提前新加权口径的起点。结果打印已完成批数，数据库错误仅输出 SQLSTATE，不输出连接串。

超过原始采样保留期后，已被异常 CPU 拉低的一分钟均值无法准确恢复。超过一分钟保留期后，旧十五分钟等权均值也无法凭现存均值和总样本数还原为正确加权结果。这些记录保持历史近似值；不得将重算完成解释成全部旧数据已经恢复准确。

## 验证与维护

验证重点是边界点数、层间样本不重不漏、迟到尾部、缺失层回退、不同样本数的加权以及批次中途失败的状态。项目的 PostgreSQL 集成测试通过独立 schema 覆盖这些行为；测试只读取显式配置的 `SERVER_MONITOR_TEST_DATABASE_URL`，不会使用应用的 `DATABASE_URL`。

保留清理按主机使用现有 `(server_id, recorded_at)` 索引定位过期候选，并在总批量内交错处理不同主机。只锁定最终删除批次，并跳过其他清理任务已锁定的记录；没有新增索引或自动调整 vacuum 参数。表膨胀、vacuum 和可见性图仍应根据部署后的数据库统计判断。
