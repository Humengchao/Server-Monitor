# 通知中心

在侧栏打开「通知中心」，添加渠道并保存，然后点击「发送测试」。测试会先进入持久化队列；「已加入队列」不等于发送成功，实际结果请查看「投递记录」。停用的渠道不能发送测试。

## 渠道配置

| 类型 | 必填配置 | 可选配置 |
| --- | --- | --- |
| Telegram | Bot Token、Chat ID | 话题 ID，用于群组中的指定话题 |
| 企业微信 | 群机器人 Webhook 地址 | 无额外加签字段 |
| 钉钉 | 自定义机器人 Webhook 地址 | 安全设置中的加签密钥 |
| SMTP 邮件 | 主机、发件地址、1–20 个收件地址 | 端口、TLS 模式、用户名和密码 |
| 通用 Webhook | HTTP(S) Webhook 地址 | Bearer Token |

### Telegram

通过 BotFather 创建机器人，填写机器人 Token 以及目标 Chat ID。私聊用户需先与机器人开始会话；群组或频道需要给予机器人发送权限。话题群可以额外填写目标话题 ID，清空该字段即取消指定话题。

消息通过 `https://api.telegram.org/bot<TOKEN>/sendMessage` 发送，使用普通文本，不使用 Markdown 解析。成功必须同时满足 HTTP 成功和响应 `ok: true`。参见 [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage)。

### 企业微信

将群机器人的完整地址粘贴到 Webhook 字段，格式为：

```text
https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<机器人key>
```

此机器人接口通过地址中的 `key` 鉴权，不填写钉钉式加签密钥。发送 `msgtype: text`，并检查响应 `errcode` 必须为 `0`；HTTP 200 但业务错误仍记为投递失败。参见 [企业微信群机器人配置说明](https://developer.work.weixin.qq.com/document/path/91770)。

### 钉钉

粘贴自定义机器人的完整地址：

```text
https://oapi.dingtalk.com/robot/send?access_token=<机器人token>
```

如果机器人安全设置启用了「加签」，同时填写其加签密钥。每次尝试都会生成新的毫秒时间戳，对 `timestamp + "\n" + secret` 使用以 `secret` 为密钥的 HMAC-SHA256，再将 Base64 结果作为 URL 编码后的 `sign` 参数发送。请保持面板主机系统时间准确。

如果机器人还配置了关键词限制，通知文本必须符合该限制，例如可配置通知固定前缀 `Server Monitor`。业务成功以 `errcode: 0` 为准。参见 [钉钉自定义机器人安全设置](https://open.dingtalk.com/document/robots/customize-robot-security-settings)。

### SMTP 邮件

主机字段只填写域名或 IP，不填写 `smtp://`、端口或路径。支持：

- `starttls`：连接后必须成功升级到 TLS；默认端口 `587`。
- `tls`：建立连接时立即使用 TLS；默认端口 `465`。

端口可单独指定。两种模式均要求 TLS 1.2 或更新版本，并验证服务器证书与主机名；没有「忽略证书」或明文回退选项。服务器若不支持 STARTTLS、证书不可信或主机名不匹配，会拒绝发送。

需要登录时，用户名与密码必须成对填写。某些邮箱需要使用 SMTP 授权码或应用密码。若邮件服务器允许免认证提交，可以同时留空。每个收件地址分别输入，不填写显示名称；正文以 UTF-8 MIME 文本发送。

SMTP 的 DATA 最终成功响应表示邮件服务器已接受邮件，不保证最终进入收件箱。拒收、反垃圾策略或后续退信仍需从邮箱服务排查。实现使用 [Go net/smtp](https://pkg.go.dev/net/smtp)，TLS 模式参考 [RFC 8314](https://www.rfc-editor.org/rfc/rfc8314)。

### 通用 Webhook

向配置的 URL 发送 JSON POST，可通过 Bearer Token 加上 `Authorization: Bearer …`。阈值告警包含 `status`、`rule`、`server`、`metric`、`value`、`threshold`、`comparator`、`message`、`timestamp`。网络通知另有 `check_id`、`source_key` 和实际 `sample`；测试消息使用 `status: test`。

只有 HTTP 2xx 才视为成功，不跟随重定向。JSON 响应若明确返回 `ok: false`、`success: false`、非零 `errcode` 或非 `0`/`200` 的数值 `code`，也视为失败。没有统一业务协议的纯文本或空 2xx 响应按 HTTP 成功处理。

每次自动重试都会携带相同的 `X-Server-Monitor-Delivery` 标识，接收端可据此去重；人工重新发送会创建新标识。每次尝试重新解析并验证目标地址，连接使用已验证地址，不使用环境代理绕过地址检查。

默认拒绝内网、回环及其他受限制地址。确实需要向内网 Webhook 或 SMTP 主机投递时，由部署管理员显式设置 `ALLOW_PRIVATE_WEBHOOKS=true`；这会允许通知模块连接私有网络，但不会关闭 TLS 验证。

## 秘密字段与编辑

渠道配置整体以应用的 `ENCRYPTION_KEY` 加密存储，包括机器人 Token、完整 Webhook URL、加签密钥、Bearer Token 和 SMTP 密码。普通渠道列表、保存响应及投递记录不会返回这些秘密。

编辑时秘密字段为空是正常状态，留空会保留已保存值。要更换秘密，直接填入新值。可选的加签密钥、Bearer Token 或 SMTP 密码可在「移除已保存的可选秘密」中明确清除；清除 SMTP 密码时也应清空用户名。必需秘密不能清空后直接启用。

修改渠道后，尚未完成的投递会使用新的配置重新排队；旧尝试的延迟结果不能覆盖新尝试。已经开始的网络请求无法撤回。停用渠道会取消排队及正在处理的记录；再次启用不会自动重发这些已取消记录。

## 规则与网络通知

在「告警」的规则编辑窗口选择一个或多个「通知渠道」。每个渠道独立生成投递记录，失败渠道不会阻塞其他渠道。

当规则未选择渠道时，继续使用规则中的旧 Webhook 配置。选择了渠道后不再同时发送旧 Webhook；若所选渠道全部停用，本轮不会发送通知。旧 Webhook 保持原投递队列兼容，新通知中心记录展示的是保存渠道的投递。

网络检查的阈值触发和恢复发送给该用户全部已启用渠道。网络样本与对应通知在同一数据库事务中提交；入队失败会回滚样本，后续采样仍可重试该状态转换。未知测量不会伪装为恢复；配置了延迟阈值时，缺少 RTT 的样本也不会恢复原告警。

## 投递记录、顺序和重试

记录包含通知内容、渠道、状态、尝试次数、入队时间、最近/下次尝试时间、投递时间以及脱敏后的错误。渠道和投递记录按用户隔离，列表使用游标分页。错误只显示本地错误分类和数值状态码，不保存远端原始响应、带 Token 的 URL 或任意网络异常文本。

主要状态为「等待投递」→「正在投递」→「已投递」；失败进入「等待重试」。自动重试从 5 秒开始指数退避，最长间隔 15 分钟。待发记录持久化在 PostgreSQL 中；进程退出或崩溃后，正在处理的记录会在一分钟租约到期后重新领取。

同一渠道、规则和服务器的触发与恢复按顺序投递。网络检查使用独立的 `network:<check ID>` 顺序标识，不同检查不会互相阻塞。人工重发继承原记录的顺序位置，恢复不会超越仍待发的触发通知。

「重新发送」必须明确确认可能重复投递，并创建带 `retry_of` 的新记录。正在处理的记录不能立即手工重发；请等待该尝试结束。若原记录仍在排队，其旧任务会同时取消。删除渠道会取消未完成任务并保留投递历史。

这是至少一次投递：远端可能已接受消息，但响应丢失或面板在确认落库前崩溃，因此自动重试也可能重复。通用 Webhook 接收端应利用投递标识去重；SMTP 邮件重试保持相同 Message-ID，但邮件服务不一定据此去重。
